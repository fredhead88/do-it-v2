# Playbooks: remove dead commands and fix the wrong operating instructions

## Goal

The six playbooks under docs/playbooks change from naming dead scripts, wrong locks, a hand rollback and the wrong pooler mode to naming the real commands and dated live facts.

In plain English: several playbooks tell an operator to run scripts at paths that do not exist, restart a job under the wrong lock, or send the API through the wrong database connection mode; this spec fixes those instructions and leaves the history in them alone.

An audit of docs/playbooks against the repo, the production database and live reads of the droplet (2026-10-15) found the statements below wrong. This spec covers six playbooks; a sibling spec (`playbooks-and-tuning-stale-b`) covers the rest of docs/playbooks, docs/tuning and docs/amazon-api-reference.md, with no shared files.

## Decisions

- Memory-guard check covers every line that mentions memory-guard (four places), because the single `not scheduled` grep could pass from one row.
- T1 cadence is read from the `deploy.sh` T1 heredoc and not hard-coded in the Goal or requirements, matching the Constraints.

- Pricing job `t2_pricing` has rows in production (28, newest 2026-10-15 08:00 UTC), so the `cron_runs` check is valid for all three units.

- The combined `amazon-tier2.log` is described as the runner's combined log that all T2 units append to (by design), read by the health tools; per-unit logs are the cron-redirect logs. No legacy or unknown writer is claimed.
- The AC2 negative check on `amazon-tier2.log` is limited to the three stale command and table lines, so the one added warning line is allowed.
- The five onboarding scripts exist under `scripts/amazon/`, so the doc's paths are corrected rather than the scripts called missing; the Goya seed script and the sales-traffic script are dropped from the doc (wrong CSV format; no `--client`). The 25% sentences are kept but reworded to say the estimate is written only when the seed script is run by hand; the runtime fallback in `pipelines/amazon/cash_cogs_injector.py` and `pipelines/quality/profit_query.py` (gated by `cogs_fallback_enabled`) is not described in the doc.

- Manual T2 and T1 runs use `flock -n` (exit 99 if already running) rather than the cron's `-w 7200` wait, so a hand run cannot hang for 2 hours.
- `data-flows.md` drops the "rsynced on every deploy mode" clause rather than keeping it: the directory it describes does not exist.
- `sp_listing_items` is the only live `sp_*` twin allowed in Storage, because its writer is verified in the repo; the other real `sp_*` tables have no verified writer for these rows.
- The memory-guard check is deliberately strict: any added line mentioning memory-guard (including the log path) must itself say `not scheduled` or `when run by hand`.

- The `t2.heartbeat` check is kept and qualified (written by whichever T2 unit finishes cleanly), with `cron_runs` added as the per-unit signal, because the runner demonstrably writes it.
- The pipeline pool wording comes from `pipeline_pool_mode()` and `api/app/config.py` only, not the db.py module docstring, which is stale.
